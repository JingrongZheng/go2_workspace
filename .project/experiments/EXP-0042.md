## Approach

2026-11-27 用户确认基础真机扬声器正常，当前先以文字输入充当 user，暂不接入麦克风与 ASR。用户选择 `kimi-k3.1-pro-highspeed`，要求关闭思考或最低强度，并提供 Kimi 官方 API 文档。

- 新增共享实现 `shared/audio/streaming_dialogue.py`、`xfyun_duplex.py`、`run_dialogue.sh`，入口 `./go2 chat`。代码仅涉及对话和播音，不接导航控制。
- 使用 aiohttp SSE 读取 Kimi `delta.content`；`delta.reasoning_content` 仅在进程内存中保留并随 assistant 历史回传，终端与 TTS 不使用该字段。按官方 K3 约定传 `reasoning_effort=low`（K3 始终思考，不传 `thinking.type=disabled`）。保留最近 10 轮完整成功对话，`/reset` 清空，`/quit` 退出。
- 默认短句队列将 LLM 生成与 TTS 解耦；每段讯飞 PCM 直接进入持续的 Go2 WebRTC 音轨。也实现 `--tts-mode duplex`，使用单 WebSocket 的 status 0/1/2、递增 seq、并发收发，但真实接口本轮有缓冲，未选为默认。
- 网络分片先按源采样率拼成 20 ms PCM，再重采样至 48 kHz，减少逐片填零与累积长度误差。播放队列约 2 秒上限，文本队列 8 段；断线或异常停止并清理后台任务与连接。每轮播完再等待下一次输入，尚无打断功能。
- `.work/dialogue.env` 已创建，600 权限且 Git 忽略；预填官方地址、模型与低强度，密钥待用户填写。API Key 不写命令参数、不输出到日志。

## Notes

资料：[Kimi API 概述](https://platform.kimi.com/docs/api/overview)、[Kimi Chat Completions / Preserved Thinking](https://platform.kimi.com/docs/api/chat)、[讯飞复刻双向流式协议](https://www.xfyun.cn/doc/spark/reproduction.html)、[aiohttp streaming](https://docs.aiohttp.org/en/stable/streams.html)。

默认按句号等切段，逗号等需至少 8 字，无标点最多 80 字切段。短回复可能在回复结束后才起播；分段韵律停顿、Kimi 最低强度下的首字延迟尚待真实联调。当前 first_audio_ms 指 PC 收到 PCM，不等于扬声器声学起播延迟。

## Results

1. 本地模拟 LLM/SSE 与讯飞/WebSocket 并发协议测试 7 项通过。关键测试强制等待首包音频被 sink 接收后，才允许大模型输出后半句，证明客户端没有等待完整回复。模拟服务不证明实际服务性能。
2. 真实讯飞 `mambo` 两句冒烟：第一句“你好，我是机器狗。”，间隔 2 秒后第二句“现在测试流式对话。”；只保存本地 WAV，不连接机器人、不播放。
   - 单会话 duplex：text_done=2175 ms，first_audio=2565 ms，26 分片，3.50 秒 WAV；出现缓冲，不能声称本次有提前出声效果。
   - 默认 sentences：first_audio=443 ms，text_done=2003 ms，27 分片，4.16 秒 WAV；后半句输入之前已收到前半句音频。
   - WAV 分别位于 `.work/audio/dialogue_duplex_smoke.wav` 与 `.work/audio/dialogue_sentence_smoke.wav`。两次是服务模式对照，不是独立性能基准。
3. 用户反馈基础真机扬声器正常，但本轮没有重测机器人，也没有运行真实 Kimi 请求。
