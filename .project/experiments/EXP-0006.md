## Approach

验证约束：D435i 在拓展坞 USB；拓展坞无线不可用且历史 USB 网卡异常；希望复用 Go2 原厂无线以免 PC 接线。本轮先验证应用层“独立 DDS 自定义话题→原厂 WebRTC”能力，再区分网络层路由/代理。无运动请求，不覆盖原厂控制/视频话题，不修改原厂配置。

由于拓展坞 SSH 无免密认证，先由 PC 在同一有线 DDS 域模拟发布者。这是服务能力预检，并非已完成拓展坞发布或无线端到端测试。使用 uuid 命名 /go2_probe/string_<nonce> 与 /go2_probe/request_<nonce>，类型 std_msgs/String 与 unitree_api/Request（所有运动字段默认，无原厂服务订阅该测试名称）。WebRTC 对三种拼写 rt/…、/…、无前导斜线…各订阅一次；同时订阅原厂 rt/lf/sportmodestate 作为阳性对照。15 秒内周期发布 nonce，读取本地 DDS 回环和 WebRTC 标记计数，并记录 DDS 订阅端点。


## Notes

源码核对：安装版 WebRTCDataChannelPubSub.subscribe 允许任意 topic 字符串发出 sub，但这只证明客户端没有名称限制，不能证明机器人服务端会动态建立对应 DDS 订阅。video 模块为 recvonly，无注册外接视频源接口。

有线地址 192.168.123.161:9991 开放，8081/22 拒绝；拓展坞 .18:22 开放但 BatchMode 认证拒绝，其 9991/8081 拒绝。直连 POST .161:9991/con_notify HTTP200，结构 data1/data2，data2=2。仅统计元信息，不保存握手密钥。


## Results

第一次默认 HTTP 环境连接失败（RemoteDisconnected/NoSdpAnswer），日志 forwarding.log。绕过测试进程对局域网 .161 的 HTTP 代理后握手、ICE、数据通道校验成功，见 forwarding-direct.log；该对比与代理干扰相符。

15 秒结果：state=300、dds_string=140、dds_request=140、webrtc_marker=0。两个测试话题的 DDS subscription endpoint 都只包含本次 probe 自身；未发现原厂服务为测试话题创建订阅。机器人报告 4G 模式，但本次信令及 ICE 明确绑定有线本地 192.168.123.222，不能把本次实验当作公网/无线测试。

未发送运动、视频或媒体开关请求。退出正常关闭 WebRTC，测试 ROS 节点销毁。


## Verification

入口 experiments/EXP-0006/probe_forwarding.py。运行时 source Humble 和宇树消息工作空间；RMW_IMPLEMENTATION=rmw_cyclonedds_cpp，ROS_LOCALHOST_ONLY=0，ROS_DOMAIN_ID=0，CYCLONEDDS_URI 绑定 enp2s0，LD_LIBRARY_PATH 添加项目 PortAudio 后，由 .work/webrtc-venv/bin/python 启动。脚本固定 .161 和 15 秒，NO_PROXY 只在此进程覆盖。不持久修改系统配置。


## 拓展坞默认路由

用户提供 ip route：default via 192.168.123.1 dev eth10 proto static metric 20100；192.168.123.0/24 直连 eth10 源 .18。该配置仅说明板端将非直连流量发往 .1，不证明 .1 存在/可达，也不证明 .1 为 Go2 原厂无线网关。此前板端抓包多次询问 .1 未见回应，仅为当时证据。需结合当前 ARP 与板端公网连通性继续核实，不直接将默认路由改为 .161。

## 网关实测结果

用户从拓展坞运行 ping -c 2 -W 1 192.168.123.1，均由 .18 返回 Destination Host Unreachable；ping 1.1.1.1 两次无回应；ip neigh show .1 为 INCOMPLETE。PC 此前同样无法 ping .1、ARP INCOMPLETE。确认当前板端配置的默认网关不能解析到 MAC；现有默认路由不是可用的共享外网路径。公网 ICMP 无回应本身不证明所有协议不可用，但结合直连网关 ARP 失败可定位当前默认路由的必要下一跳不可达。

## DDS↔WebRTC 封装规则专项验证

本轮按用户要求只调查应用层数据通道，不再以拓展坞网络共享为主线。

1. 被动观察：入口 inspect_bridge_topics.py，结果 bridge-envelopes.log。/webrtcreq、/webrtcres、/xfk_webrtcreq、/xfk_webrtcres 都存在原厂 bare DDS 发布与订阅端点。WebRTC 会话正常收到状态160帧；/webrtcreq 与 /webrtcres 均0帧；/xfk_webrtcreq 和 /xfk_webrtcres 各1帧且出现在握手阶段。仅记录长度、JSON字段类型，不记录认证内容。xfk请求为 data1/data2/data3/data4 字符串对象、响应不是直接 JSON，结合信令源码应按握手专用通道处理，不能当作普通业务数据管道直接写入。

2. 独立 API：入口 probe_custom_api.py，custom-api.log。用随机私有 /api/go2_probe_<uuid>/request 和 response，类型 unitree_api/Request、Response，api_id9001仅位于私有测试话题，没有任何原厂动作服务处理。WebRTC发送3次 req；DDS服务端接到0条。随后本地DDS基线3次请求均得到3条响应，但WebRTC自定义响应0条；同会话原厂状态201帧。WebRTC订阅私有响应话题后，DDS发现仍只有测试节点订阅者。不能只靠 req/Response 格式让任意新增服务自动过桥。

3. 既有字符串出口：入口 probe_existing_pipe.py，existing-pipe.log。仅对 /webrtcres（非动作请求话题）发3条约数百字节 msg/topic/data 文本信封，topic为随机 go2_probe/pass_<uuid>，data只有marker/sequence；不覆盖原厂状态/相机话题，不写xfk认证话题。DDS本机回环3条，原厂订阅端点存在；直接监听RTC原始字符串/二进制帧中的nonce仍为0，同会话原厂状态141帧。说明该具体信封不构成可用上行出口；未知真正封装规范，不能因此认定此话题绝对不可用。

以上全部使用 .161 有线信令与有线ICE，是服务能力预检而非无线或板端最终链路测试；均正常关闭会话，无运动命令、无服务配置修改。官方文档正文仍受访问拦截，未找到官方通用数据透传注册规则。社区驱动作者旧README明确称WebRTC pub/sub话题有限（https://github.com/legion1581/go2_python_sdk/blob/main/README.md）；仅作为社区实现说明，不替代官方规范。

当前真正缺口是原厂 webrtc_bridge 服务端的话题/类型映射与输入信封规则。读取原厂服务配置/接口规范后才能设计下一项针对性测试，不继续枚举随机topic或填充控制字段。拓展坞 .18 SSH需用户认证且不是已确认的原厂服务运行位置；原厂 .161 SSH22拒绝，不假定能从拓展坞直接修改原厂WebRTC服务。

检索结论：有原厂系统修改与协议分析的社区线索，但本轮未找到带可复跑证明的“拓展坞任意传感器数据→原厂WebRTC无线→PC”现成实现。更精确的后续调查对象是原厂桥接服务的类型/话题注册及固件差异，而非重复部署已有PC客户端。

## Conclusion

当前服务未自动转发本次测试的两类自定义 DDS 话题，不能直接把 D435i 发布为新增话题就期待原厂 WebRTC 无线输出。此负面证据不证明服务端绝对禁止扩展或不存在专门注册/配置接口；也未覆盖所有消息类型和命名。

## Continuation

最新停点：普通topic、自定义API、既有webrtcres标准信封均无转发，详见专项验证。需要官方服务端自定义数据入口的规范/配置（topic、type、session routing、封装及尺寸/频率限制）；不再将网络共享作为当前方向。公开架构图证明模块互通，但不规定任意内容的接入方式。

当前默认网关 .1 已验证不可达，不再重复相同 ping/抓包。应用层自定义 String/Request 未被原厂 WebRTC 自动转发；网络层现有默认路由未提供共享上网。要坚持原厂无线承载拓展坞 D435i，须获取并验证原厂服务扩展/网关配置接口或原厂系统相应管理权限；不能通过只改 PC 桥接保证实现，也不擅自把板端网关改成 .161。以下为此前调查线索。

后续若坚持复用原厂无线，需要找到原厂 WebRTC 自定义数据源注册/配置接口，或核实 Go2 系统是否提供拓展坞网络路由/代理。未验证网络层转发，不能声称 Go2 已能共享其 4G/WiFi 给拓展坞。原厂 .161 SSH22 拒绝，拓展坞 .18 需用户本机认证；无需重复已完成的 PC 有线与状态阳性对照。板端 ip route 可先由用户提供，用于判断是否存在默认网关，不能用拓展坞自身 IP forwarding 开关替代 Go2 转发能力。
