# Go2 开发周报｜2026 年第 47 周

统计范围：2026-11-16—2026-11-19（截至周四；本周记录主要发生于11月17—19日）。

本周围绕宇树 Go2 完成开发环境搭建、通信架构学习、键盘运动控制、原厂无线接口验证和外接传感器接入。主要成果是建立PC端ROS 2开发基线，并打通“D435i → 机载小电脑 → WiFi → PC显示与双视频保存”的独立链路。目前尚未开展导航或强化学习算法复现；无线吞吐和深度测量可信度仍需进一步验证。

## 通信专项进展

本周分别验证了“PC直连原厂DDS”“PC通过WebRTC访问原厂服务”和“PC访问机载小电脑上的自定义采集程序”三条链路。它们使用的协议、访问对象和扩展能力不同；PC本地出现ROS 2话题，不代表跨设备一段必然使用DDS。

### A. 有线DDS／ROS 2基线（EXP-0001、EXP-0002、EXP-0004）

链路：PC ROS 2节点 → Cyclone DDS → PC以太网 → Go2内部以太网络 → 对应原厂DDS服务；状态和传感器数据沿反向路径返回。

- PC使用Humble及unitree_ros2消息定义，配置RMW、DDS域和网卡，完成发现及实际收包。该模式不要求通过SSH到机载小电脑启动客户端，也不是向其Foxy发出“查询所有话题”的请求。
- PC有线地址192.168.123.222，拓展坞192.168.123.18、运控192.168.123.161；实测后两者可达。拓展坞SSH是另一项管理能力，不等同DDS通信本身。
- 读取/sportmodestate、/utlidar/cloud与/frontvideostream，并实现/api/sport/request高层运动请求。前置视频收到非空消息与完整解码图像分别记录，不混为同一验收。
- XT16目标192.168.123.20无ARP响应，说明该次尚未建立到目标的二层可达性；没有证明是ROS驱动问题，也不能直接判定雷达损坏。

### B. 原厂无线服务与PC ROS 2桥接（EXP-0003）

控制方向：PC键盘节点 → PC本地ROS 2请求话题 → 自编桥接 → 社区WebRTC客户端 → Go2原厂WebRTC模块 → 原厂运动服务。

数据方向：Go2原厂状态／相机／体素点云 → 原厂WebRTC模块 → PC社区客户端及解码 → PC本地ROS 2话题／预览。

- 使用unitree_webrtc_connect社区客户端，实现连接与协议处理；项目自行编写ROS 2消息转换、独立键盘请求入口和预览功能。应区分社区客户端与官方SDK接口。
- LocalSTA模式在同一热点下实测，限定无线ICE地址以排除有线参与；用户确认拔掉有线后仍能控制移动。一次8秒独立订阅测试收到111帧状态、31帧图像和42帧体素点云；后续独立预览进程复测12秒收到239帧状态、163帧图像。
- 将OpenCV预览与网络接收分到不同进程，解决此前显示阻塞引发状态超时的问题；该软件问题与后续D435i链路的低吞吐分开记录。
- LocalSTA访问原厂无线系统，D435i后续访问拓展坞无线网卡；两者不是同一设备的同一接口。原厂无线控制可用，不代表拓展坞已联网。

### C. 原厂4G／公网Remote路径（EXP-0003、PLAN-0002）

预期链路：PC互联网接入 → 账号与设备SN的云端信令 → WebRTC ICE协商 → Go2互联网接入（包括其原厂4G）；业务数据依据实际协商可直连，也可经TURN转发。

- 用户确认App启用公网远程连接及机器狗4G状态。项目实现--remote、--sn、区域选择、终端交互账号认证，并与键盘控制终端分开运行。
- 公网连接使用账号／SN发起设备会话，不把App显示的wwan0私网地址当成PC可直接访问的公网地址。PC也需要自己的互联网出口。
- 原厂4G上网主体与拓展坞是两个访问对象。本周没有证据证明拓展坞可以直接借用该4G作为通用网关。
- Remote配置与模拟测试通过；用户曾提供持续收包和连接中断日志，但尚缺包含两端接入网络、实际ICE路径、时延、运动反馈及断连行为的完整异地验收。不能将设备4G开启、Remote入口存在或局域网无线控制成功单独等同跨城任务完成。
- 4G及可能的云转发涉及数据费用，本次D435i正式录制在局域网完成，不通过原厂公网会话传输。

### D. 自定义数据借用原厂管道的边界（EXP-0006）

围绕“机载小电脑DDS → Go2原厂WebRTC → PC”进行针对性测试，并保持原厂状态收包作为阳性对照。

- 私有String／Request话题本机DDS回环正常，而WebRTC未收到自定义内容。
- 独立私有API本地请求响应正常，但同一会话未出现相应WebRTC请求／响应过桥。
- 将既有webrtcres视为通用文本出口的具体封装测试同样没有成功；结合源码确认SDP信令话题不能直接当作业务数据入口。
- 拓展坞默认网关192.168.123.1没有ARP响应，原路由配置也没有提供已验证的共享上网路径。

结论限于这些测试：尚未找到可直接复用的通用扩展入口，继续需要原厂服务端映射、类型注册或网关配置规范。没有修改固件或原厂服务；不把负面结果扩大成“所有自定义扩展均不可能”。

### E. 拓展坞独立WiFi与双视频链路（EXP-0007、EXP-0008）

链路：D435i → USB 3 → 拓展坞C++ RealSense采集程序 → JPEG压缩 → SSH/TCP → USB WiFi网卡 → 办公室AP → PC WiFi → 解码显示与MP4保存。

- 识别新网卡0bda:c812被option串口驱动接管，针对Jetson内核5.10.104-tegra构建88x2cu驱动；采用按USB ID匹配的局部绑定，避免全局移除option。配置开机加载和热插拔服务，并验证WiFi连接及已保存网络自动连接。
- 正式录制TCP端点为PC 192.168.110.120 → 拓展坞192.168.110.87:22，确认业务走无线地址，未复用旧有线SSH套接字。
- 该录制链路不依赖ROS、原厂WebRTC或Go2原厂4G。机载C++程序直接调用SDK，PC端解码并生成RGB／深度伪彩两个视频。设备联网成功后，也为后续部署自定义服务和传感器程序提供了网络基础；这些扩展尚未逐项验收。
- 双路640×360@15原始RGB数据约166Mbps，已改为JPEG压缩传输；正式视频各保存86帧。采集配置和MP4标称15fps不能代表实际无线收帧率。
- 独立TCP实测约0.419Mbps且超时，ping最大约421ms。此证据把低帧率问题定位到需要优先调查的网络路径，但尚未确定AP、频段、驱动或其他具体根因。PC可见spin220_5G，尚未验证切换效果。

本周通信成果：建立有线开发基线，打通原厂无线控制和机载外设独立WiFi回传两条路径，同时明确两者的扩展边界。下一步重点是稳定吞吐、断连恢复和跨地域网络验收，而非再次重复已完成的消息编译或网卡识别。

## 3. 主要问题与限制

1. **无线视频帧率不足。** 独立于相机的TCP测试约0.419Mbps，并出现发送超时；无线ping最大约421ms。说明当时网络路径吞吐和时延不适合当前双流，但尚未定位至AP、频段、驱动或其他具体根因。不能直接断言换5GHz必然解决。
2. **深度数值尚未验证。** 当前使用固定0.2—5m Jet伪彩；用户反馈不同远近区域颜色近似、约2m目标的颜色与预期不符。仅凭伪彩图不能认定测距正确。现有视频没有原始Z16深度，且经过有损编码，无法可靠回溯测量；RGB与深度也未进行像素对齐。
3. **XT16未确认数据。** .20无ARP响应，接线、供电、真实IP、网络分段或驱动配置仍待分辨。不能用原厂雷达点云替代验收。
4. **跨城扩展数据通信未完成。** 当前D435i成功链路为同一局域网WiFi；没有证明Go2原厂4G/WebRTC能替机载小电脑转发任意新增传感器数据。跨城仍需明确可用网络出口、VPN或服务端扩展方案。

## 4. 下周建议顺序

1. 充电并恢复测试后，优先验证深度：在已知0.5、1、2m目标处读取原始深度和单位，对比现场实测；加入距离读数、色条和原始深度保存，再决定后续感知用途。
2. 建立无线吞吐基线：记录AP/频段、实际fps、Mbps与丢包/时延；对比2.4GHz、5GHz及有线，再按结果调整压缩和传输策略。
3. 核对XT16实际网络与设备配置，先证明其自身数据可达，再接入ROS 2和PC显示。
4. 在局域网链路稳定后，选择并验证跨地域网络方案，补齐自定义服务往返和断连恢复。
5. 传感器与通信达到可用基线后，选择第一个导航复现任务，定义场景、输入、成功率和对照基线；强化学习复现随后按资源与目标安排。
