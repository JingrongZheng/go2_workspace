# 同次采集生成导航地图与扩展地图

**2026-11-24排期更新：** 用户将高斯功能明确排到最后，当前先做实验室L1＋IMU经WiFi的PC端导航，D435i/XT16后续接入。本文件保留为后期RGB-D数据合同，不再要求先完成双地图才允许首阶段导航。首批没有RGB-D的数据不能直接用于RGB-D高斯重建；后续补采相机并与已有导航地图配准。当前执行入口为real-deployment.md；下文早期“仿真阶段就要验证/两份成果均为当前目标”的时间要求已由此更新。

2026-11-23最终选择：两份成果均为当前目标，不是导航完成后再考虑扩展。导航由DDDMR基线承担；扩展地图已确定为3D高斯地图，具体高斯建图实现尚未选择。共享原始数据、标定、时间和空间关联，避免只留导航地图导致以后重新扫描。

## 架构

```text
仿真或实机的同次采集
  雷达 + IMU + RGB + 原始深度 + 标定/TF + 时间戳
                          |
               不可覆写的原始数据集
                    /           \
          DDDMR建图与导航       扩展地图构建
          地面/障碍/pose graph  3D高斯（实现待选）
                    \           /
                 同一地图身份及可查询的坐标变换
                          |
            扩展层生成目标 -> DDDMR导航执行
```

不假定DDDMR输出可直接转成高斯地图。两条构建过程可以独立优化轨迹，但必须保留数据关联、尺度和跨地图变换，检查对齐误差。导航目标既可以由用户指定，也可以由扩展层产生；不以固定点位编号作为整个系统唯一任务接口。

## 原始数据合同

| 保存项 | 用途与要求 |
|---|---|
| 雷达原始PointCloud2 | 原坐标系、逐点时间/ring等字段保留；只保存累积/体素点云不足以重跑前端 |
| IMU | 采集时间、单位、轴向、频率；与对应传感器身份关联 |
| RGB图像 | 原始或可控质量压缩，保留每帧时间；不要只留最终MP4 |
| 原始深度 | Z16/16UC1及明确depth_scale，或有单位的32FC1；无损保存，不用伪彩视频代替 |
| CameraInfo/标定 | RGB和深度内参、畸变、分辨率、RGB-depth外参及对齐状态；不能套示例内参 |
| TF与安装标定 | base、雷达、相机body/optical frame的明确关系；动态TF、静态TF、标定版本均存 |
| 时间与帧关联 | 使用消息采集时间而非只保留到达时间；记录跨设备时差及同步策略、丢帧和配对残差 |
| 位姿轨迹 | 保存原始里程计、回环优化后的轨迹/关键帧身份与版本；可按图像采集时刻查询相机位姿 |
| 采集元数据 | session/map ID、场景/路线、传感器身份、参数、源码版本、数据完整性清单 |

以可回放rosbag2和导出索引/标定文件为准备方向，具体录制器尚未实现。不硬编码未知话题名；启动前核对实际消息类型与发布频率。原始记录与派生地图分开目录，后处理不改写原始文件。

此前D435i双视频是展示产物，没有完整原始深度/标定数据，不能将其列为本合同已经通过的采集样本。

## 位姿和地图的一致性

导航在线帧通常使用map→odom→base_link。相机每帧位姿需结合该时刻机体位姿和相机外参推导；若有后端回环，不能仅用录包时TF冒充最终优化轨迹。对两条地图分别优化的情况保存T_nav_from_extension及尺度/轴向定义，不能仅重命名frame_id宣称对齐。

首次只验证小区域：在两个地图中选同一门口/墙角/目标，将扩展地图目标转换到导航地图，检查空间位置和导航终点一致。具体容差由尺寸与控制余量确定。

## 仿真阶段就要验证

1. 场景同时有雷达/IMU和RGB-D输出；相机图像需有纹理与覆盖，不能只有用于RViz着色的导航点云。
2. 同次记录先保存原始数据，记录足够重叠的多视角观测；导航路线覆盖不自动等于相机覆盖。
3. 不重新运行仿真采集，用同一份记录构建DDDMR导航地图和高斯地图样本；允许不同的软件环境和后处理。
4. 保存共同地标/位姿关联，验证地图对齐，再从扩展层产生一个目标交给导航。
5. 单独标注使用仿真真值还是传感器估计位姿；先有双地图样例，再扩大到整栋楼和真实采集。

未观察到的面、过曝/模糊或深度无效区域无法保证靠后处理补出。因此目标是尽早通过小样本证明数据可复用，避免系统性重采，而不是承诺未来任意地图算法都不需补采。
