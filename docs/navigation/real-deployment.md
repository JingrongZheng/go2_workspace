## 当前决定与范围

- 先在实验室小环境，用Go2内置L1与IMU建立传感器估计、建图、重定位和平地导航闭环。
- PC负责算法计算、数据记录和RViz，继续使用Humble/Docker；实机不启动Gazebo。机载电脑只在需要时承担驱动/采集/转发，不在上面部署整套LIO/DDDMR。
- 通信固定实验室同一局域网WiFi；不使用4G/公网Remote/TURN作为本阶段数据链路。
- XT16送修，暂不依赖；D435i可用，但首阶段不加入导航前端。后续接XT16/相机，再做高斯地图。
- 用户所给L1规格作为硬件描述：360°×90°、标称0.05m近盲区、30m@90%反射率、21600有效点/秒、230g、75×75×65mm。实际频率/字段/噪声/可用距离以采集为准，点率不是算法输出帧率。
- 前端方案：用户2026-11-24已确定采用Point-LIO；ROS2具体实现/commit仍待锁定并验证。FAST-LIO2暂不作为本阶段主线。用户随后要求硬件测试延后，R0保持待执行，不自动连接机器人或启动采集。

## 计算与通信位置

```text
方案A：原始数据能够直接穿过Go2原生WiFi接口（待验证）
Go2内部L1原始点云＋配套IMU ──同一局域网WiFi──> PC
PC：数据适配/录包 → LIO → DDDMR建图/定位/规划 → RViz
PC：速度适配器 ──已验证的WiFi高层控制链路──> Go2运控

方案B：原生WiFi没有暴露合格原始流
Go2内部L1原始点云＋IMU ──机内以太网──> 小电脑（采集/转发）
小电脑 ──已修复无线网卡＋WiFi──> PC（全部算法与显示）
PC ──WiFi高层控制链路──> Go2运控
```

先检查A，不假设可用；A不可用则执行B，不必让整个导航栈迁到小电脑。两方案都满足PC经WiFi工作。之后D435i的USB驱动、XT16驱动可以在小电脑采集，经同一WiFi送PC；独立传感器不自动进入Go2原厂WebRTC管道。

两个IP要分清：Go2原生WiFi接口IP用于原厂无线控制；小电脑无线网卡IP用于SSH和传感器转发。旧地址192.168.110.87、10.186.248.47仅为历史，不当作本次现值。当前没有进行远程连接或网络探测。

### 现有WebRTC桥的限制（已读本地实现）

`shared/go2_webrtc_state.py`订阅`rt/utlidar/voxel_map_compressed`，`receive_cloud`只生成XYZ三字段、12字节点步长，并以PC接收时刻打消息时间戳。它适合查看原厂体素地图，不是可直接用于LIO的原始扫描。

因此：
- 已有WiFi控制/视频可用，不等于L1原始点云、逐点时间、同步IMU已经可用。
- `/go2/webrtc/points`暂不接到Point-LIO/FAST-LIO2作为原始输入，也不冒充逐点时间缺失已修复。
- 首先核查Go2暴露的原始DDS/传感器流、类型、字段和采集时钟。若数据在机内可用但不能直接经原生WiFi到PC，用小电脑转发并保留原始采集时间。
- 不改传感器内部串口归属、不停原厂主控；独立L1 SDK教程中的串口直连步骤不能直接套用到Go2内置雷达。
- WiFi多播、AP客户端隔离、ROS域、QoS、RMW网卡绑定都单独检查。SSH/ping通不等于DDS已通。

## IMU和里程计选择

官方unilidar_sdk能输出L1点云与L1内置IMU，且给出两坐标系关系。优先核查这对同传感器来源数据，减少跨源时间/外参问题。它不等于已经证明Go2能通过当前无线接口提供这对原始流。

Go2机体IMU、L1内部IMU、D435i IMU是不同传感器，不能混用名称或套用同一外参。如果只能拿到机体IMU，则需先核实时间基准、频率、单位、轴向和雷达—机体IMU外参。SDK接口中存在imu_state，不代表其时间质量自动满足高频LIO。

### 两类路线不能混称

1. **本项目首选验证：雷达＋IMU融合里程计。** 在PC运行LIO，给DDDMR提供连续的位姿和TF。
   - 宇树官方point_lio_unilidar已适配L1，但官方主线为ROS1/Noetic。
   - `dfloreaa/point_lio_ros2`声明支持L1/L2和Ubuntu22.04/Humble，代码有UNILIDAR逐点time处理；它是社区移植，需锁定commit、依赖并编译/录包验证，不把README支持声明当本项目通过。
   - FAST-LIO2也可作为候选，但不能仅换节点名或假设默认雷达解析器已支持Go2原始格式。
2. **作者可选的dddmr_odom_3d。** 用已有里程计速度和IMU姿态构造粗略3D里程计；不是激光惯性紧耦合LIO，也不能替代点云同步/去畸变。只有机体速度质量先通过实测才考虑对照，不能无声切换并宣称LIO已跑通。

LIO内部逐点更新与对外odom/TF发布频率分开设置，避免照搬高频无降采样发布导致ROS/DDS负载和重复时间戳问题；频率按数据时钟、DDDMR消费周期与PC性能实测确定。

前端输入审计通过前，不直接搬默认配置中的频率、饱和值、acc_norm、外参或blind。官方L1示例里blind=0.5m，不等于硬件标称0.05m盲区；软件可额外剔除近点，也需结合自遮挡和安装实测。

## 与DDDMR的接线

```text
原始L1＋同步IMU → LIO → 连续里程计/基座坐标适配 → /odom
        原始/合格去畸变点云 → DDDMR特征与地面处理
                         → DDDMR位姿图/角点/平面/地面地图
                         → MCL地图定位＋全局/局部规划
                         → /cmd_vel → Go2高层运动适配器
```

DDDMR仍接外部里程计模式（示例参数名wheel_odometry，不意味着机器人必须有轮子）；不要同时启用另一条纯激光前端并争抢同一里程计输出。

第一阶段保留DDDMR建图格式，不能仅保存LIO的scans.pcd就认为已有其MCL所需位姿图、关键帧和地面图。点云输入是当前扫描及真实frame，不把已经转到世界坐标的累计地图再次当传感器扫描输入，以免重复变换。

TF发布责任：

| TF边 | 发布方 |
|---|---|
| odom→base_link | LIO输出经真实IMU—机体外参换算后的唯一发布方 |
| map→odom | 地图优化/定位阶段对应的唯一发布方，按工作模式切换 |
| base_link→lidar_link / imu_link | 实测或核实的安装外参 |
| 后续base_link→camera及optical frame | 相机安装标定与原厂内部标定 |

不能只改frame_id来把IMU位姿变成机体位姿。实机use_sim_time=false，不启动gz_pose_to_ros2或initialize_demo_pose。已知地图通过人工3D Pose Estimate或真实重定位初始化，不调用Gazebo真值辅助入口。

新建实机启动文件，不复用run_local.sh simulation/navigation。网络配置允许跨设备（不能继承ROS_LOCALHOST_ONLY=1），按实测选择域/RMW并绑定WiFi接口；保持仿真域83与实机启动隔离。EXP-0020 已准备 L2 前端、录包、RViz 和 DDDMR 建图入口，见 [实机 README](../../shared/dddmr/real/README.md)。实机 WiFi 原始话题仍待验证。

## 作者指南要求与本项目实际修改点

| 项目 | 当前原演示 / 作者硬件 | 实机L1必须做什么 |
|---|---|---|
| 雷达模型 | Go2模拟16线VLP / Airy倾斜45° | L1为非重复扫描；核对投影行列、角域、scan_period与stitcher_num，不套固定16线或Airy100行参数 |
| TF/坐标 | 示例x=.2,z=.22,pitch45°等 | 按Go2实际L1安装与机体坐标建立，先静止检查地面方向，再运动 |
| 地面筛选 | ground_fov上下界/方位区间等 | 用实际扫描与外参调ground_fov、距离、自遮挡、地面连通；不靠扩大膨胀补出未观测地面 |
| 里程计 | 仿真模型位姿 | 真实LIO输出，检查轴向、单位、连续性、重力方向及与扫描时刻关系 |
| 点云缓存 | 演示扫描方式 | 先统计帧率与覆盖，再调非重复扫描累积，保存延迟/畸变对照 |
| 建图 | 示例已有地图 | 实验室重新建图，保存完整pose graph/关键帧/角点/平面/地面及标定版本 |
| 机器人包络 | 模拟Cuboid | 实测机体/四肢运动包络和雷达位置，配置碰撞体，不能只量躯干 |
| 速度/轨迹 | 模拟器默认可较快 | 按已验证真机起步、转向和停止范围限制；先测最小可靠步态速度，不盲设极低导致原地前倾 |
| 局部障碍 | 演示静态/动态层 | 核对当前扫描、已知地图和实时障碍分工；确认地面/空洞/下落边缘不被误当安全 |
| 保存/定位 | 示例地图路径 | 新地图身份与路径、人工初始位姿、丢失后的恢复，不使用旧Gazebo地图 |

作者要求连续且不突跳的里程计，建议误差小于约10%；这不是厘米级保证或本项目已通过指标。ROS2重定位修正放map→odom，不将突跳灌入连续odom。

## 分阶段实验与验收

| 阶段 | 工作 | 通过证据 / 继续条件 |
|---|---|---|
| R0 只读链路 | WiFi路径A/B选择，获取原始点云与配套IMU；静止录60–120秒 | 原始字段/采集时间/频率/字节率/QoS/丢帧/时钟偏差/单位与坐标说明；体素XYZ不当原始输入 |
| R1 离线LIO | 回放静止、手动短直线/转向/往返记录；PC计算 | 静止漂移、轨迹连续性、已量距离误差、墙面重影、CPU/延迟；无真值或机体姿态替代计算结果的假验证 |
| R2 小环境建图 | LIO供odom，DDDMR外部里程计建图；先手柄/现有键盘移动 | 地面覆盖、墙体与柱子边缘合理；绕行回来检查重叠，保存完整地图并能重载 |
| R3 重定位 | 新会话载地图，人工提供粗位姿，原地及手动小范围走动 | 雷达与地图对齐，map/odom责任明确，定位丢失能被发现，不下自主速度 |
| R4 速度适配预检 | /cmd_vel先只打印/录制，核对速度、角速度、方向、超时与唯一发送方 | 旧指令不重放、状态失联停发；另验证机器人端指令超时/看门狗和现场停止手段，不能把PC尝试发零速度当作断链后机器人已收到；手动停止优先级有效 |
| R5 实验室平地闭环 | 明确空旷短目标，再绕单个障碍 | 记录到达误差、路径、停车距离、失败原因和WiFi延迟；先不走楼梯或盲区 |
| R6 换雷达/相机 | XT16修好后独立适配；D435i原始RGB-D及CameraInfo | 修改驱动/外参与预处理，重验同步和数据质量，不替换整个导航接口 |
| R7 高斯地图 | 单独RGB-D采集/算法选型，配准导航地图 | 原始深度及RGB/位姿/内外参齐全，重建样例与跨地图目标对齐 |

默认不主动触发R1的实机运动。先准备R0数据，再由用户确认当前连接、上电和现场条件后实施对应实验；这些是阶段输入，不在本计划阶段反复要求用户接线。

### 观察反馈与参数迭代

每次实验记录：数据包、参数快照、版本/标定、时间段、手动/自主模式和简短结果。工具从记录中取数，用户主要反馈现象、发生时刻、姿态和截图/短视频。一次只改一组明确相关参数，保留前后对照：

| 用户观察 | 首先核对 | 可能调整的层 |
|---|---|---|
| 墙面重影、转弯甩图 | 原始点时间、IMU偏移、外参、轨迹 | 数据/LIO，先不改规划器 |
| 地面缺一大片 | 原始地面观测、覆盖路线、安装姿态、ground分层 | 投影/ground_fov/累积与采集；不假填成可走 |
| 机器人不走、身体前倾 | 发出的实际速度、控制模式、可靠起步阈值 | 高层控制适配与轨迹速度范围 |
| 绕障太近或路径穿物体 | 障碍是否进入局部观测、TF时刻、Cuboid | 感知/碰撞包络/距离阈值 |
| 地图跳位置 | 原始odom与map→odom分别检查 | 初始化/定位；不能用真值覆盖 |
| RViz卡顿 | 接收频率、数据年龄、CPU、WiFi丢帧分别统计 | 显示降采样/QoS/网络，不破坏原始录包 |

## 后续传感器与高斯的边界

D435i以后用于局部深度或RGB-D高斯重建时，需要原始深度与内外参、时间及相机位姿，伪彩视频不能代替。按本次优先级，首批只采L1/IMU，不能承诺该批数据可直接生成RGB-D高斯地图；后续要补采图像并与导航地图配准。先保留可复用的原始雷达/IMU/轨迹/TF和地图版本，不强制现在运行高斯算法或接入相机。

需要用户在实测前提供/确认：L1是否仍为出厂安装、相对机体的安装位置/朝向与离地高度（可先描述后测量）、当前WiFi网段与可达IP、静止状态。未知值不填成示例数值。
